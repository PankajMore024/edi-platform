Architecture Overview

One engine. Two worlds. A universal document in the middle.

The platform translates business documents between the customer’s world (Shopify, QuickBooks, a CSV, their DB) and the partner’s world (Walmart, Target, big vendors) that demands EDI. Everything translates to and from one invented format — the canonical document. That single idea keeps the rest simple.

Mappings · the heart of it

Two kinds of map, one hub, zero partner logic in code

A map is a small declarative file: “this field here = that position there.” The engine only interprets maps — so onboarding a partner is a new map, reviewed and tested, never a code change.

Partner (EDI) map

canonical ⇄ a partner’s X12 — their quirks, qualifiers, and version. Validated by edi-map.schema.json.

Connector map

canonical ⇄ a customer system’s shape — a Shopify order, a CSV column layout — written in the same DSL.

WAS → NOW The old is_td5 / inc_vadd boolean columns and if/else branches become data in a map. That’s the moat.

Version handling · 4010 · 5010 · …

The engine is version-neutral

A version difference is just structural variation — the map absorbs it, exactly like partner quirks. The interpreter never branches on version.

Role 1 — Selector

Picks the map by (partner, docType, direction, version). Read from GS08 inbound, from config outbound.

Role 2 — Envelope value

Stamped into GS08. ISA/GS structure is stable across the 40x0/50x0 families, so the envelope carries version without branching.

Role 3 — Validation key

Selects the right per-version X12 dictionary. Reference data — thin in v1, grows in Phase 4.

v1: target 4010 (dominant in retail/dropship); add versions per real partner demand — each new version is a new map, never engine work.

AI onboarding · the moat

The sandbox is the oracle. The agent loops until it’s right.

The sandbox and the onboarding agent aren’t two features — the sandbox is the deterministic environment and verifier; the agent is the actor that authors a map by looping against it. A wrong map simply fails and bounces back, so nothing unproven survives.

STEP 1ProposeAgent drafts a candidate map from the partner IG + sample files.
→
STEP 2RunSandbox executes: deterministic engine → validate → diff vs expected.
→
STEP 3ReportStructured, machine-readable failures — what, where, expected vs got.
→
STEP 4ReviseAgent reads the report and fixes the map.
→
STEP 5ApproveHuman signs off → immutable published map, pinned to the relationship.
↺  Steps 2–4 repeat automatically until the report is green — no human in that inner loop.
